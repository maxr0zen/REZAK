## 1. Продукт и исходные условия

Приложение принимает запись стрима с диска, а впоследствии автоматически обнаруживает и записывает эфир Twitch. Оно находит интересные законченные эпизоды, предлагает монтаж и экспортирует:

- самостоятельные вертикальные ролики 9:16 для Shorts и TikTok;
- горизонтальные подборки 16:9 для YouTube.

Приоритет контента: реакции и разговорные стримы. Игровые стримы — следующий профиль.

Известное оборудование: 8 ГБ VRAM и 16 ГБ RAM. Точная видеокарта, доступный encoder, размер/квантование Bonsai2 и её runtime пока не установлены. В исходном окружении использовались Windows и PowerShell; при запуске в другой среде проверь фактическую ОС. Локальная Bonsai2 уже есть. Не заменяй её и не скачивай другие большие модели без необходимости и согласования расходов диска.

Проект контейнеризируется через Docker Compose. Данные и кеши переживают пересоздание контейнеров. Начальный результат сохраняется локально; автоматическая публикация не входит в MVP.

## 3. Архитектурные решения

Базовый стек: Python, FFmpeg/ffprobe, faster-whisper как первый кандидат ASR, Pydantic, SQLite, FastAPI после появления API и веб-интерфейса. Совместимые версии выбери по фактической среде и зафиксируй lock-файлом. Не выбирай версию Python только по принципу «самая новая»: проверь поддержку библиотек распознавания и GPU.

Пайплайн:

```text
Источник → проверка медиа → подготовка аудио и proxy
→ ASR с таймкодами → кандидаты → оценка Bonsai2
→ уточнение границ → монтажный план → валидация
→ превью → правки → рендер → проверка экспорта
```

Основные модули: SourceAdapter, MediaProbe, Transcriber, CandidateGenerator, BonsaiAdapter, EditPlanner, PlanValidator, Renderer, JobRunner, ArtifactStore.

Это модули приложения, а не обязательные отдельные сетевые сервисы. В Compose начни с `app` и `worker`, при необходимости из одного образа с разными командами. `recorder` добавь при реализации Twitch. CLI может предшествовать API и работать в том же образе.

Bonsai2 сначала подключается к существующему runtime на хосте через настраиваемый адрес. Не навязывай новый сервер модели. Подтверди реальный endpoint, формат запросов, structured output и возможность работы с изображениями короткими тестами. При нестабильном tool calling используй фиксированные стадии и валидируемый JSON.

SQLite хранит задачи, состояния, метаданные и обратную связь; видео лежит в файловом хранилище. Для app/worker используй короткие транзакции и проверенную конкурентную работу; для первоначальной простой схемы ограничь запись через один управляющий компонент. SQLite размещай на локальном Docker volume, вне синхронизируемого OneDrive и сетевых каталогов.

На старте не добавляй Redis, PostgreSQL, Kubernetes, отдельный vector database server, обучение своей модели и универсальный видеоредактор без доказанной необходимости.

## 4. Контракт между моделью и монтажом

Модель возвращает структурированный монтажный план, а код проверяет его и формирует операции FFmpeg. Произвольные shell-команды от модели не исполняются.

План содержит версию схемы, идентификатор источника, профиль выхода и список интервалов с абсолютными `start_ms`/`end_ms`, выбранными шаблонами и ссылками на исходные слова/кадры. Принять диапазоны `[start, end)` и целые миллисекунды; для точного декодирования учитывать исходные PTS и time base.

Проверяй существование источника, допустимость границ, ограничения профиля, интервалы потерь записи, повторяющиеся сегменты и разрешённые операции. При невалидном ответе — ограниченное число попыток исправления, затем понятная ошибка с сохранением диагностики.

Запускай внешние процессы через массив аргументов без shell-интерполяции. Поддержи отмену, timeout, exit code и ограниченный журнал stderr без секретов. Точные срезы и фильтры обычно требуют перекодирования; не обещай точный монтаж через stream copy между ключевыми кадрами.

## 5. Качество отбора

Главная единица результата — законченный эпизод с понятной подводкой и завершением.

- Разговор: история, вопрос и ответ, аргументированный тезис, неожиданная развязка.
- Реакция: необходимый исходный контекст → реакция стримера → завершение.
- Игра: подготовка → действие → исход → реакция.

Не своди интересность к громкости, крикам или всплескам чата. Начни со смысловых окон расшифровки с перекрытием, объединения соседних кандидатов и уточнения границ. Аудиосигналы и чат — дополнительные признаки. Позже добавь выборочный анализ кадров, в том числе тихих участков без речи.

У каждого кандидата сохраняй причину выбора, ссылки на доказательства, необходимость внешнего контекста, пригодность для short/подборки и замечания. Допускай результат «подходящих моментов недостаточно».

Вертикальные ролики и горизонтальная подборка получают разные планы из общей библиотеки кандидатов. Поддержи ручной шаблон webcam/основного контента; для реакций предусмотрена двухзонная композиция. Не обрезай вслепую центр кадра. Не удаляй все паузы автоматически.

Субтитры пересчитываются по монтажному плану. Проверяй кириллицу, наличие шрифтов, переносы строк, читаемость и синхронизацию. Сохраняй исходник и исходную расшифровку неизменными.

RAG подключай после baseline: сначала примеры хороших/плохих решений, затем поиск по библиотеке предпочтений и контексту стримера. Сравни варианты на одних исходниках по принятию кандидатов и объёму правок. Правила экспорта задаются конфигурацией, а не извлечённым текстом.

ArtCraft/FilmCraft не являются основой MVP. Позже можно проверить экспорт редактируемого таймлайна через отдельный адаптер. Не привязывай внутреннюю схему плана к одному редактору.

## 6. Ресурсы, данные и устойчивость

При 8 ГБ VRAM и 16 ГБ RAM первоначально планируй тяжёлые стадии последовательно: ASR → освобождение памяти → Bonsai2 → рендер. Возможность одновременной работы определяют замеры.

Проверь доступ к GPU внутри контейнера, производителя GPU, драйверы и доступные кодировщики. Не считай наличие видеокарты доказательством поддержки CUDA или NVENC. Оставь CPU-профиль для минимальных проверок; ускорение подключай отдельной конфигурацией.

Не отправляй в модель весь многочасовой эфир. Ограничивай контекст, batch, число и разрешение кадров. При OOM меняй параметры в пределах ограниченной политики повторов; не повторяй бесконечно тот же запрос.

Каждая стадия сохраняет артефакт. Ключ кеша учитывает источник, конфигурацию, модель, prompt и версию стадии. Смена оформления субтитров не запускает ASR повторно. Правки пользователя имеют собственные версии и не теряются при повторном анализе.

Выход сначала пишется во временный файл, проверяется, затем становится финальным. Проверяй свободное место, поддерживай отмену и восстановление задач после перезапуска. Не удаляй оригиналы без явной политики пользователя.

Для Twitch раздели обнаружение эфира и захват видео. План: EventSub/Helix для состояния, Streamlink как кандидат recorder, запись восстанавливаемыми частями, дедупликация событий и карта «часть → media timestamp → время эфира». Учитывай пропуски, смену разрешения, рекламу и задержку чата. Захват не должен останавливаться из-за сбоя анализа.

Токены не попадают в Git, образы и логи. Текст стрима, чата и RAG-документов рассматривается как данные, а не инструкции. Для API с доступом к файлам ограничь разрешённые каталоги и защити от обхода путей. На старте интерфейс доступен локально. Перед публикацией контента нужны соответствующие настройки и поручение пользователя.
