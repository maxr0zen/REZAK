# План развития обработки REZAK

Цель — сократить число запросов MiniMax на одну запись, улучшить отбор и кадрирование TikTok и позволить разным стримам одновременно занимать разные ресурсы. План основан на обсуждении SupoClip и очередей Celery. Реализация идей собственным кодом.

## 1. Замерить текущую обработку

- [ ] Выбрать фиксированный набор из свежего стрима 5opka и отмеченных пользователем удачных и неудачных эпизодов. Для быстрых сравнений взять один и тот же фрагмент с разговором, реакцией на экран и переходом активности.
- [ ] Для каждого этапа фиксировать число запросов, повторов, попаданий в кеш, время ожидания и токены, если их вернул API. Для TikTok считать кандидатов до дедупликации, после неё, после проверки и после рендера.
- [ ] Сравнивать прогоны с холодным и тёплым кешем отдельно. Сохранять метрики рядом с идентификатором записи, моделью и версией правил.

## 2. Улучшить отбор TikTok через MiniMax

- [ ] Использовать кандидатов из общего анализа расшифровки. На первом проходе запрашивать компактный результат с ID сегментов, объяснением ценности эпизода, силой захода и типом кадрирования.
- [ ] Объединять близкие варианты по доле перекрытия. Выбирать лучший по оценке и наличию завязки и развязки. Хранить альтернативу, если она добавляет смысловой контекст.
- [ ] Пакетно ранжировать короткий список перед индивидуальной проверкой. Отсеивать обычные реплики без конкретного поворота, шутки или реакции. При отклонении кандидата брать следующего из запаса.
- [ ] Проверять начало и развязку одним запросом с соседними репликами. Включать завершение той же мысли и реакцию на донат или видео. После выбора границ оставить около 500 мс с каждой стороны в пределах исходника.
- [ ] Проверять ID, принадлежность исходнику, длительность и отсутствие дублей локально. Кешировать проверку с учётом модели, версии инструкции и границ.
- [ ] Сравнить размер окон на фиксированном наборе. Оценивать валидность ответов, пропуски сильных моментов на стыках, время и число запросов.

Готовность этапа — число запросов на проверку снизилось на контрольной записи, сильные эпизоды сохранились, а принятые клипы проходят ручную проверку начала и конца.

## 3. Укрепить работу с API

- [ ] Проверить поддержку строгого структурированного вывода на используемом endpoint MiniMax. Оставить локальную валидацию через Pydantic.
- [ ] Различать ошибки сети, ограничение частоты, обрыв по лимиту, пустой ответ и нарушение схемы. Для временных сбоев применять ограниченные повторы, для обрыва уменьшать объём требуемого ответа или дробить только проблемный пакет.
- [ ] Показывать в журнале этап, пакет и причину повтора. Сохранять успешные пакеты и продолжать с них после повторного запуска. Ограничивать одновременные запросы по провайдеру.

Готовность этапа — тесты воспроизводят обрыв JSON, пустой ответ и временную ошибку сети. Повтор использует готовые пакеты, а необработанные диапазоны видны в журнале.

## 4. Улучшить кадрирование и разбор отзывов

- [ ] Проверить YuNet с резервом на Haar, устойчивость детекции по нескольким кадрам и фильтрацию резких скачков области лица.
- [ ] Для реакции на экран сохранять значимую область экрана и вебку. Если точный кроп не найден, использовать безопасный полный кадр. Учитывать возможность увидеть второе лицо внутри видео. СДВГ-фон для 5opka выключен.
- [ ] Разобрать существующие оценки REZAK по категориям «момент», «границы», «кадрирование» и «блюр». Связывать замечания с таймкодами и версией правил, чтобы превращать повторяющиеся дефекты в контрольные примеры.

Готовность этапа — на контрольных фрагментах важное действие остаётся в кадре, область вебки не прыгает, а результаты можно сравнить с пользовательскими оценками.

## 5. Разделить очередь по ресурсам

- [ ] Разделить задачу записи на подготовку, распознавание, анализ и рендер. Сохранять артефакт и состояние каждого этапа для восстановления после сбоя.
- [ ] Сузить общий блокировщик до этапов Whisper и локального Bonsai. Оставить один слот GPU.
- [ ] Дать MiniMax общий лимит для всех записей. Начать с трёх одновременных запросов суммарно. Оставить отдельный слот FFmpeg, чтобы рендер мог идти одновременно с облачным анализом другой записи.
- [ ] Проверить две записи одновременно в текущей локальной очереди. Измерить общее время, загрузку GPU, CPU и диска и поведение отмены.
- [ ] Если понадобятся независимые процессы или несколько машин, оценить Celery с Redis и отдельными очередями по этапам. Перед переносом проверить идемпотентность, восстановление после падения воркера и отсутствие двойного запуска.

Готовность этапа — две записи могут одновременно выполнять разные этапы, конкурирующие GPU-задачи идут последовательно, а отмена или повтор одной записи не затрагивает другую.
